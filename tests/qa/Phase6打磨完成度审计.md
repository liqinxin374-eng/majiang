**问题 P6-01【Major】头像 PNG 完全未做压缩。**

单张接近 1MB 的图片用作头像，属明显未优化项。头像在界面上的实际显示尺寸远小于原图分辨率。四张头像占了 `dist` 总体积（6.55MB）的 **54%**。

**建议**：压缩为 WebP 或缩放到实际显示尺寸的 2 倍分辨率后再压缩。保守估计可从 3.55MB 降到 200KB 以内，减少约 3.35MB，直接让安装包与首屏加载显著变小。这是当前投入产出比最高的一项优化。

**问题 P6-02【Minor】头像资产重复存放。**

四张头像同时存在于**项目根目录**与 `public/` 目录，内容相同。根目录副本不参与构建，属冗余文件，容易造成改了一处忘了另一处。建议删除根目录副本，只保留 `public/`。

同样情况：`theme_classic_thumb.png`、`theme_sci_fi_thumb.png` 也在根目录，`style.css.bak`（65,994 字节）为遗留备份文件，建议一并清理。

## 三、音频打磨审计

### 3.1 核心发现：项目中没有任何音频文件

全项目检索 `*.mp3` / `*.wav` / `*.ogg` / `*.m4a`（排除 `node_modules`），**结果为 0**。

所有声音由 Web Audio API 的 `OscillatorNode` 实时合成，实现位于 `src/app/main.js:277-312`。

### 3.2 事件覆盖清点

操作提示与新手引导均已接入真实状态，`action-guide` 还带了 `role="status"` 与 `aria-live`，无障碍处理到位，这点值得肯定。

### 3.3 问题 P6-04【Major】"背景音乐"并非音乐

`refreshBackgroundMusic()`（`main.js:306-312`）实现如下：

```js
BACKGROUND_MUSIC_TIMER = setInterval(() => playGameSound('background'), 1400);
```

配合 `background: { frequency: 110, duration: 0.5, type: 'sine' }`，实际效果是：

> **每隔 1.4 秒播放一次 0.5 秒的 110Hz 正弦波单音。**

这是一个低频单音循环嗡鸣，不构成任何旋律、和声或节奏，在听感上更接近设备故障提示音而非背景音乐。开发计划清单标记的是「添加背景音乐**开关**」，从字面看开关确实存在，标记 `[x]` 不算错；但若对外表述为"已有背景音乐"，与实际体验不符。

**风险**：长时间游玩时，持续的 110Hz 低频重复音容易引起烦躁。且该定时器在 4 小时压测中会触发约 **10,285 次**音频节点创建，是内存压测的重点观察对象（已写入 `真机验收测试计划.md` 第 8.4 / 8.5 节）。

**建议（三选一，由用户决策）**：

1. **降级预期**：默认关闭背景音乐，文档改称"背景音效开关"，不宣称有 BGM。成本最低。
2. **补真实资源**：引入一段循环 BGM 音频文件（建议 OGG，128kbps，30–60 秒循环，约 500KB–1MB）。体验提升最大，但增加包体。
3. **改进合成**：保持零资源方案，但把单音改为多振荡器和弦进行，加入包络与节奏变化。折中方案，需要一定音频设计能力。

### 3.4 问题 P6-05【Minor】音效为单振荡器占位音

7 类音效均为「单个振荡器 + 单一频率 + 指数衰减」结构（`main.js:294-303`），无分层、无采样、无起音塑形（仅 `exponentialRampToValueAtTime` 做尾部衰减）。

以「杠」为例：160Hz 锯齿波持续 0.18 秒。麻将杠牌在真实体验中期待的是清脆的牌撞击声，而锯齿波低频音听感更接近电子蜂鸣。

**判定**：功能正确、有反馈、能区分不同操作（频率与波形各不相同，可辨识度尚可），但属**占位级音频**，不是打磨后的产品级音效。

**建议**：若追求上线品质，为出牌、碰、杠、胡四个高频关键操作补真实采样音效（四个短音合计约 100–200KB 即可），其余保留合成方案。这是性价比最高的音频改进路径。

### 3.5 音频小结

| 层面 | 判定 |
|---|---|
| 事件接通完整性 | ADEQUATE — 10/10 计划项全部接通 |
| 开关与音量控制 | ADEQUATE — 三层控制齐全，关闭后不产生节点 |
| 音频资源质量 | **INCOMPLETE** — 零音频文件，全为占位级合成音 |
| 背景音乐 | **INCOMPLETE** — 实为 110Hz 循环嗡鸣，非音乐 |

**音频判定：CONCERNS。** 不阻塞发布（有声音、可关闭、不报错），但"Phase 6 音频打磨完成"的表述不成立。准确说法是"音频事件已全部接通，资源为占位级"。

### 4.2 问题 P6-06【Major】性能门存在覆盖盲区

`scripts/checkPerformance.js:39` 的图片统计条件为：

```js
if (/theme_.*\.png$/i.test(file)) themeImages += (await stat(file)).size;
```

该正则**只匹配文件名以 `theme_` 开头的 PNG**，导致以下资产完全不在性能门监控范围内：

| 被漏掉的文件 | 体积 |
|---|---|
| `dist/avatar_cyber_bird.png` | 994,125 B |
| `dist/avatar_neon_wolf.png` | 952,508 B |
| `dist/avatar_matrix_cat.png` | 921,199 B |
| `dist/avatar_commander.png` | 850,161 B |
| `dist/themes/xianxia_cloud_bg.jpg` | 856,838 B |
| **漏统计合计** | **4,574,831 B（约 4.36MB）** |

**后果**：性能门报告"主题图片 1.79MB，通过"，给人以包体受控的印象；而 `dist` 实际情况是：

| 类型 | 文件数 | 合计 |
|---|---|---|
| PNG | 6 | 5,508,426 B（5.25MB） |
| JPG | 1 | 856,838 B（0.82MB） |
| SVG | 108 | 304,620 B（0.29MB） |
| CSS | 1 | 81,692 B |
| JS | 1 | 78,184 B |
| HTML | 1 | 35,417 B |
| **dist 总计** | **118** | **6,865,177 B（6.55MB）** |

**图片实际占 6.07MB，是性能门口径（1.79MB）的 3.4 倍。** 换句话说，现在这道性能门**监控不到包体的主要构成部分**，即使有人再塞进去 4MB 头像图，它依然会报"通过"。

**建议修复**（`scripts/checkPerformance.js`）：

1. 把图片统计改为匹配全部 `.png` / `.jpg` / `.jpeg` / `.webp`，而非仅 `theme_*.png`。
2. 增加 `dist` 总体积上限（建议先设 8MB，优化头像后收紧到 3MB）。
3. 现有 JS 250KB / CSS 150KB 上限过于宽松（当前只用了不到 10%），建议收紧到 60KB / 40KB，让门槛真正具备预警能力。
