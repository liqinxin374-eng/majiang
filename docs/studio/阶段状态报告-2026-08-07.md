**复核过程中抓到两次问题**（记录在案，因为它们说明"报告通过"不等于"真的通过"）：

1. eng-lead 首次报告「155 测试全过」。主理人独立复跑，实测 `165 tests / 164 pass / 1 fail`，退出码 1。
   - 失败项：`not ok 160 - encodeWebSocketText uses a 64-bit length header for payloads >= 65536 bytes`
   - 根因定位：**测试断言写错，实现无问题**。`tests/webSocketServer.test.js:35` 硬编码期望长度 `70000`，
     但帧内装的是完整 JSON（`{"type":"room:updated","room":{"big":"` + 70000 个 x + `"}}`），实际 **70041** 字节。
     同文件第 26 行的 16 位测试就用对了 `Buffer.from(JSON.stringify(message)).length`，64 位这条漏了。
   - 已修正并复验通过。

2. **工具陷阱**：`node --test` 的输出若直接接 `grep` 管道，退出码会被管道末端命令覆盖，
   导致失败被"洗白"。必须重定向到文件再读。

## 五、本轮新发现的重大风险

### R-0（新增，高）：项目没有任何版本控制

执行 `git rev-parse --is-inside-work-tree` 返回 `fatal: not a git repository`。

这意味着：

- 本轮 eng-lead 对 `main.js` / `accountService.js` / `webSocketServer.js` 的大规模重写**无法回滚**
- 无法 diff，无法审查改了什么
- 无法定位"上次还好好的，什么时候坏的"
- 团队协作、发布分支、热修回滚全部无从谈起

对一个即将上架、刚刚经历大重构的项目，这是比 B1~B6 任何一条都更危险的状态。
**建议优先于其他所有发布准备工作处理。**
