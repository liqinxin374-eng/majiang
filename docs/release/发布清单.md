## 二、P0 阻塞项详情与验证证据

### B1 [P0] 三端构建产物不同步，待验收的 APK 是旧代码

这是本次核对发现的**最严重问题**：现在挂着"待真机验收"的那个 APK，装的不是最新代码。

| 位置 | JS 文件名 | 大小 | 生成时间 |
|---|---|---|---|
| `dist/assets/` （最新网页构建） | `index-C49pLpvX.js` | 78,184 B | 2026-08-03 13:40 |
| `android/app/src/main/assets/public/assets/` | `index-NLWjnQ38.js` | 77,874 B | 2026-07-31 13:46 |
| `ios/App/App/public/assets/` | `index-DoUJATjE.js` | 70,829 B | 2026-07-22 11:26 |

- `app-debug.apk` 生成于 2026-07-31 13:48，基于 7-31 的资源 → **不含 8-3 的全部改动**。
- iOS 工程停留在 7-22，**落后两个版本**。

**处置**：真机验收前必须重跑 `npm run build` → `npm run android:sync` → `npm run ios:sync` → 重新出包。用旧包验收出来的结论无效。

**验收标准**：`dist/assets/`、`android/.../assets/public/assets/`、`ios/App/App/public/assets/` 三处的 JS/CSS 文件名与字节数完全一致。

### B2 [P0] iOS 工程缺失全部游戏图片资源

`ios/App/App/public/` 目录下**只有** `assets/`、`cordova.js`、`cordova_plugins.js`、`index.html`。

已确认缺失：

- `mahjong-tiles/`（**108 张麻将牌 SVG，全部缺失**）
- `themes/`（主题背景图 `xianxia_cloud_bg.jpg`）
- `avatar_commander.png`、`avatar_cyber_bird.png`、`avatar_matrix_cat.png`、`avatar_neon_wolf.png`（4 张玩家头像）

对照 Android 侧 `android/app/src/main/assets/public/` 是齐全的（含 `mahjong-tiles/`、`themes/`、4 张头像）。

**后果**：现在拿到 Mac 上直接打包 iOS，游戏能启动，但**牌面全是空白**、头像全是裂图。这会让 iOS 真机验收得出完全错误的结论。

**处置**：重跑 `npm run ios:sync` 并逐目录核对；如果 sync 后仍缺，需排查 `public/` 目录是否在 7-22 之后才建立。

**验收标准**：`ios/App/App/public/mahjong-tiles/` 下有 108 个 SVG 文件。

### B3 [P0] Android 正式签名与混淆未配置

`android/app/build.gradle` 现状：

```gradle
buildTypes {
    release {
        minifyEnabled false
        proguardFiles getDefaultProguardFile('proguard-android.txt'), 'proguard-rules.pro'
    }
}
```

- **没有任何 `signingConfigs`**，`release` 也没有 `signingConfig` 引用 → 只能产出未签名包，Google Play 直接拒收。
- `minifyEnabled false` → 包体偏大（当前 debug 包 18.3 MB）。

**处置**：

1. 生成正式签名密钥库（keystore），**这是不可再生资产**：
   ```
   keytool -genkey -v -keystore facai-mahjong-release.jks -keyalg RSA -keysize 2048 -validity 10000 -alias facai
   ```
2. keystore 与密码**不入 git**，放 `android/keystore.properties`，并写进 `.gitignore`。
3. keystore 文件与密码由用户离线备份至少两处。**丢了就永远无法更新这个 App**。
4. 在 `build.gradle` 中接入 `signingConfigs.release`。
5. 建议同时开启 Google Play App Signing（Google 托管签名，本地密钥丢失可申诉恢复）。

**验收标准**：`./gradlew bundleRelease` 产出已签名的 `.aab`，`apksigner verify` 通过。

### B4 [P0] 联机服务器地址写死为本机，移动端必然连不上

`src/app/main.js` 三处（第 1539、1581、1643 行）：

```js
const protocol = window.location.protocol === 'https:' ? 'wss' : 'ws';
const host = window.location.hostname || 'localhost';
ROOM_SOCKET = new WebSocket(`${protocol}://${host}:3001/ws`);
```

在 Capacitor 打包的 App 里，WebView 的 `location.hostname` 是 `localhost`（Capacitor 内置 scheme），于是客户端会去连**手机自己的 3001 端口**——那里什么都没有。

**后果**：Android / iOS 安装包里的「创建房间」「加入房间」「断线重连」**全部失败**，只会显示"房间服务器未启动"。单机模式不受影响。

**处置（二选一，需用户拍板）**：

- **方案 A（推荐，联机作为卖点）**：部署正式服务器 + 域名 + HTTPS/WSS 证书，前端改为读取构建期环境变量（如 `VITE_GAME_SERVER`），移动端固定指向线上域名。注意 iOS ATS 与 Android `cleartextTrafficPermitted` 默认都禁止明文，**必须用 `wss://`**。
- **方案 B（首发降级）**：移动端**隐藏联机入口**，首发只发单机版；补丁说明与商店描述里不得出现"联机对战"字样，否则属于虚假宣传，商店可驳回。

**验收标准**：真机（非同一局域网）能成功创建房间并让第二台设备加入。

### B5 [P0] 账号、金币、战绩只存在内存中

`server/accountService.js` 第 9-15 行：

```js
export class AccountService {
    constructor() {
        this.users = new Map();
        this.transactions = [];
        this.matches = [];
```

文件顶部注释也写明："账号服务目前使用内存仓库……后续接入 SQLite 时，只需要把 Map 的读写替换为 schema.sql 对应的表操作。"

`server/database/schema.sql` 已经写好了完整表结构（users / coin_transactions / matches / match_players），但**没有被任何代码引用**。

**后果**：服务器一重启或崩溃，所有玩家的账号、密码、金币、战绩、排行榜**全部归零**。这在正式运营中是不可接受的事故，也会直接引发玩家投诉与商店差评。

**处置（二选一，需用户拍板）**：

- **方案 A**：接入 SQLite 持久化（schema.sql 已就绪，工作量可控），并建立定时备份。
- **方案 B（首发降级）**：首发不开放注册与金币，只保留游客本地模式；商店描述不得出现"金币""排行榜""战绩"。

**验收标准**：重启服务进程后，已注册账号能正常登录，金币余额与战绩不变。

## 三、P1 高优先级问题（不阻塞发布，但强烈建议首发前修）

### P1-1 iOS 屏幕方向与 Android 不一致

`ios/App/App/Info.plist` 的 `UISupportedInterfaceOrientations` 包含 `UIInterfaceOrientationPortrait`，iPad 项还包含 `PortraitUpsideDown`。

而 Android 侧 `AndroidManifest.xml` 已强制 `android:screenOrientation="landscape"`。

游戏为横屏设计（`mobile-landscape.css`），iOS 允许竖屏会导致布局错乱。

**处置**：iOS 只保留 `LandscapeLeft` 与 `LandscapeRight`。

### P1-2 iOS 设备能力配置为过时的 armv7

`UIRequiredDeviceCapabilities` 填的是 `armv7`（Capacitor 老模板残留）。App Store 现在要求 arm64。

**处置**：改为 `arm64`，或直接删除该键。

### P1-3 iOS 开发区域写成英文

`CFBundleDevelopmentRegion` = `en`，但 App 是纯中文。

**处置**：改为 `zh-Hans`，避免 App Store 默认语言显示为英文。

### P1-4 生产包内残留测试模式代码

`src/app/main.js` 第 507、534 行存在「暗杠测试」「补杠测试」的作弊式手牌注入逻辑（直接把玩家手牌替换成 4 张 8 万等）。

已确认 `index.html` 中**没有**对应的触发按钮，玩家正常操作无法进入，风险等级不高。但代码仍打进生产包，存在被控制台调用的可能。

**处置**：正式包中移除，或用构建期 `import.meta.env.DEV` 条件编译隔离。

### P1-5 WebSocket 实现只支持极短消息，联机同步存在硬上限

`server/webSocketServer.js` 第 12 行：

```js
if (payload.length >= 126) throw new Error('实时消息过长，请拆分后发送。');
```

且 `socket.on('data')` 只解析单帧、未处理分片帧 / ping-pong / close 帧。

一局四人麻将的房间状态 JSON（含手牌、牌河、副露）**必然远超 125 字节**，广播时会直接抛错。

**本条为发布核对中发现的疑似缺陷，需由主理人转严守真 / 程基岩复核确认**——如果证实成立，B4 的"方案 A 部署服务器"就不只是改地址，联机链路需要先做实质性修复；届时建议直接走 B4 方案 B（首发单机）。

### P1-6 无隐私政策与用户协议文件

项目根目录下不存在任何 privacy / 隐私 / terms / 协议 文件。

Google Play 与 App Store **均强制要求**可公开访问的隐私政策 URL。详见 `商店提交清单.md`。

## 四、版本号策略

### 4.1 语义化版本（SemVer）规范

采用 `MAJOR.MINOR.PATCH`：

| 位 | 何时 +1 | 麻将项目里的例子 |
|---|---|---|
| MAJOR | 破坏性变更、玩法规则大改、存档不兼容 | 从血战到底扩展为多玩法且旧存档失效 |
| MINOR | 新增功能，向后兼容 | 新增新主题、新增观战功能 |
| PATCH | 只修 bug，不加功能 | 修复定缺面板在小屏被裁剪 |

**首发版本号建议：`1.0.0`**

理由：`开发计划清单.md` 九个阶段的功能项已全部标记完成，属于功能完整的首个公开版本，不宜用 0.x（0.x 在惯例上表示 API/玩法仍会破坏性变动，会削弱玩家与审核方的信任）。

### 4.2 三端版本号映射

| 平台 | 字段 | 首发取值 | 规则 |
|---|---|---|---|
| Web | `package.json` → `version` | `1.0.0` | 唯一真源（single source of truth） |
| Android | `versionName` | `"1.0.0"` | 与 `package.json` 完全一致 |
| Android | `versionCode` | `10000` | 公式 `MAJOR*10000 + MINOR*100 + PATCH`，**必须严格单调递增** |
| iOS | `MARKETING_VERSION` | `1.0.0` | 与 `package.json` 完全一致 |
| iOS | `CURRENT_PROJECT_VERSION` | `1` | 每次提交 TestFlight/审核 +1，同一 MARKETING_VERSION 下不可重复 |

**versionCode 公式示例**：

| 版本 | versionCode |
|---|---|
| 1.0.0 | 10000 |
| 1.0.1 | 10001 |
| 1.1.0 | 10100 |
| 2.0.0 | 20000 |

**当前不一致，需修正**：

| 位置 | 现值 | 应改为 |
|---|---|---|
| `package.json` → `version` | `1.0.0` | ✅ 保持 |
| `android/app/build.gradle` → `versionName` | `"1.0"` | ❌ 改为 `"1.0.0"` |
| `android/app/build.gradle` → `versionCode` | `1` | ❌ 改为 `10000` |
| iOS `MARKETING_VERSION` | 待确认 | 设为 `1.0.0` |

> ⚠️ Android 的 `versionCode` 只能增不能减。首发若用了 `1`，后续想改成公式制会被迫从更大的数开始，因此**首发就定 10000** 最省事。

### 4.3 版本发布节奏建议

- **紧急热修**：PATCH +1，走简化流程（见 `商店提交清单.md` 第五章）。
- **常规更新**：PATCH / MINOR，2～4 周一次，避免频繁提审消耗审核额度。
- **版本冻结**：提交商店前 48 小时进入冻结期，只允许修 Blocker，禁止改文案（详见 `本地化覆盖.md` 的字符串冻结规则）。
