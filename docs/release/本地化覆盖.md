# 发财麻将 本地化覆盖评估与计划

- 文档负责人：发布运营负责人（release-ops-lead）
- 创建日期：2026-08-07
- 结论摘要：**首发只做简体中文（zh-Hans），不做多语言**。但需在首发前完成三项低成本的「不做本地化也必须做」的工程准备，避免未来扩展时被迫重写界面。

## 二、是否需要多语言：评估结论

### 结论：**首发不做多语言。**

### 2.1 支持「不做」的理由

**① 目标玩法本身高度地域化。**
四川麻将「血战到底」是川渝地区玩法，核心受众就是中文玩家。定缺、查大叫、查花猪、刮风下雨、退税这些概念，即便翻译成英文，不懂中式麻将的玩家也无法理解。这不是翻译问题，是**玩法认知门槛**问题——需要配套的规则教学，而不是一份词表。

**② 术语翻译无行业标准，机翻必错。**

| 中文术语 | 直译陷阱 | 说明 |
|---|---|---|
| 定缺 | "Fixed Lack" | 需意译为 "Void Suit"，且要配教学 |
| 血战到底 | "Fight to the Death" | 语义完全跑偏，实指 "Play Until Three Winners" |
| 刮风下雨 | "Wind and Rain" | 实指杠牌计分（Kong Scoring） |
| 查大叫 | "Check Big Call" | 实指流局罚分（Tenpai Penalty） |
| 查花猪 | "Check Flower Pig" | 实指未清缺门罚分 |
| 退税 | "Tax Refund" | 实指杠分返还（Kong Score Reversal） |
| 龙七对 | "Dragon Seven Pairs" | 需注明是含四张相同牌的七对 |

这套术语没有权威英译标准。做，就必须找**懂中式麻将的母语译者**，不是普通译员，更不是机翻。成本与风险都不低。

**③ 首发有更该花力气的地方。**
`发布清单.md` 里有 6 项 P0 阻塞（联机不可用、数据不持久化、签名缺失、资源不同步、命名冲突、iOS 缺图）。在这些没解决之前投入本地化，是**优先级倒置**。

**④ 没有 VO，未来扩展成本天然低。**
项目音效全部是无语义提示音（摸牌、出牌、碰、杠、胡、倒计时），**没有任何配音**。这意味着未来做多语言时，不需要重录语音、不需要口型对齐、不需要音频资产管线——成本只有纯文本翻译。**这是推迟本地化的底气**：晚做不会更贵。

**⑤ 数据驱动比拍脑袋准。**
首发后看 Google Play Console / App Store Connect 的地区安装分布，用真实数据决定第二语言，比现在猜要靠谱得多。

### 2.2 反方意见与回应

> "繁体中文（zh-Hant）成本很低，为什么不顺手做？"

**回应：低但不为零，而且不只是转字。** 台湾、香港、澳门有各自的麻将玩法（台湾 16 张麻将与四川 13 张差异极大），繁中用户看到「血战到底」会有玩法预期错位。此外简繁转换存在用词差异（如「界面/介面」「设置/設定」「音效/音效」），机械转换会显得粗糙。

但繁中确实是**投入产出比最高的第二语言**，因此列为 P1，见第四章。

## 三、风险提示（即使不做多语言也必须处理）

### 3.1 [P1] 界面文案与代码逻辑耦合

`src/app/main.js` 第 156-160 行：

```js
if (message.includes('警告') || message.includes('严重')) {
} else if (message.includes('定缺')) {
} else if (message.includes('已胡')) {
```

**这是用中文字符串内容来做程序分支判断。**

问题在于：这不只是本地化障碍——**任何一次文案微调都可能悄无声息地改变程序行为**。比如把「已胡」改成「已胡牌」，这条分支仍然命中；但改成「胡了」，分支就静默失效，日志高亮消失，且不会报任何错。

**处置建议（P1，与本地化无关也该修）**：改为在产生日志时携带显式的类型字段（如 `logTerminal(text, { level: 'warn' })`），由类型而非文本内容驱动分支。

### 3.2 [P0-法务] 应用图标含「發」字的商店合规风险

`ios/真机测试准备.md` 中记载图标为「麻将牌和红色『發』字」。

「發」是麻将中的發财牌，在中文语境下是标准麻将符号。但在部分海外市场的商店审核视角下，**红色「發」+ 麻将 + 金币 + 排行榜**的组合，容易被判定为**赌博类应用**（gambling），触发：

- Google Play 的赌博政策审核，可能要求 18+ 分级或在特定国家下架
- App Store Guideline 5.3（Gaming, Gambling）审核，历史上对麻将类 App 审核偏严

**处置**：

1. 首发若只面向中文市场，风险可控，可保留。
2. 商店分级问卷中**必须如实申报「模拟赌博元素」**（有虚拟金币、有排行榜）。隐瞒被查出的后果远重于如实申报。
3. 商店描述必须明确写出：**虚拟金币不可充值、不可提现、不可交易、无任何现金价值**。
4. 未来出海时，考虑准备一套无「發」字的替代图标。

> 本条与 `商店提交清单.md` 第四章「分级与合规」联动，请一并阅读。

### 3.3 [P2] 昵称校验正则限定中文，未来会挡住外语用户

`server/accountService.js` 第 19 行：

```js
if (!/^[\u4e00-\u9fa5A-Za-z0-9_]{2,16}$/.test(normalizedName))
```

字符集为「中日韩统一表意文字基本区 + 拉丁字母 + 数字 + 下划线」。

**当前无影响**（首发只面向中文用户，且该规则能有效防止表情符号、零宽字符等昵称攻击，是一个不错的安全默认值）。

**未来扩展时需注意**：日文假名、韩文谚文、俄文西里尔字母、阿拉伯文全部会被拒绝。届时需扩展为 Unicode 属性转义（如 `\p{L}\p{N}`）并配合规范化与敏感词过滤。

### 3.4 [P2] RTL（从右向左）语言的特殊挑战

`AndroidManifest.xml` 已设置 `android:supportsRtl="true"`（Capacitor 默认）。

但麻将游戏的 RTL 适配远比普通 App 复杂：**牌桌座次（东南西北）、出牌方向、手牌排列顺序都有方向语义**，简单镜像会让牌桌逻辑错乱。

**建议**：阿拉伯语、希伯来语列为**明确不支持**，不进入任何本地化规划。投入产出比极低。

### 3.5 [P1] 硬编码文案无统一出口，改文案要翻整个代码库

目前改一句提示语，需要在 `index.html` 和 `main.js` 之间搜索定位。约 250～320 条文案分散在 6 个文件里。

这不仅是本地化问题，也是**日常运营效率问题**——每次微调文案都要碰代码、重新构建、重新测试。

## 四、本地化覆盖计划与优先级

### P0 — 首发前必做（简体中文范围内的工程准备）

这三项**不做多语言也要做**，成本低，能避免未来推倒重来。

| # | 任务 | 负责方 | 验收标准 |
|---|---|---|---|
| L0-1 | 统一产品名，同步 `capacitor.config.json` / `strings.xml` / `Info.plist` / `index.html` 标题 / `package.json` | 程基岩 | 五处名称完全一致 |
| L0-2 | `Info.plist` 的 `CFBundleDevelopmentRegion` 由 `en` 改为 `zh-Hans` | 程基岩 | App Store 默认语言显示为简体中文 |
| L0-3 | 撰写简体中文版隐私政策与用户协议，托管至公开 HTTPS URL | 用户 + 发布运营 | 两个 URL 可匿名访问 |

### P1 — 首发后 1～2 个版本内（i18n 地基）

**注意：这不是"做翻译"，而是"让未来能做翻译"。** 即使永远只有中文，这些改造也能让文案维护成本大幅下降。

| # | 任务 | 说明 |
|---|---|---|
| L1-1 | 建立 `src/locales/zh-CN.json` 字符串表 | 把约 250～320 条硬编码文案抽出，key 用语义命名（如 `game.dingque.title`） |
| L1-2 | 实现轻量 `t(key, params)` 函数 | **不引第三方 i18n 库**——项目坚持零运行时依赖的原生 JS 风格，自研约 30 行足够，且不增加包体 |
| L1-3 | `index.html` 改用 `data-i18n` 属性，启动时填充 | 保持 HTML 结构不变，渐进式改造 |
| L1-4 | 修复 3.1 的文案驱动分支逻辑 | 改为显式类型字段 |
| L1-5 | 服务端错误改为返回错误码 + 默认中文文案 | 前端按码查表，服务端不承担多语言职责 |
| L1-6 | 建立字符串冻结流程 | 见第六章 |

**建议**：L1 改造**与其他重构一起做**，不要单独开一个「i18n 重构」分支。项目当前已通过 108 项测试，`项目架构说明.md` 明确要求"不在已通过测试的代码上进行大范围无依据重写"——本地化地基应当遵守同一条纪律，**逐文件小步迁移，每步跑一次全量测试**。

### P2 — 数据驱动决策后（真正的多语言）

**触发条件（满足任一才启动）**：

- 非中文地区安装量占比 > 15%
- 商店评论中出现 ≥ 20 条语言相关诉求
- 用户明确决定出海

**语言优先级排序**：

| 优先级 | 语言 | 理由 | 预估工作量 |
|---|---|---|---|
| 1 | 繁体中文 zh-Hant | 无玩法认知门槛，转换成本最低；台港澳市场 | 1～2 人日（需人工校对用词，非机械转换） |
| 2 | 英文 en | 覆盖面最广；海外华人 + 麻将爱好者社群 | 5～8 人日（**必须找懂中式麻将的译者**） |
| 3 | 日文 ja | 麻将文化深厚，但日麻规则与川麻差异极大，需大量规则说明 | 8～12 人日 |
| 4 | 韩文 ko | 有麻将受众但规模较小 | 5～8 人日 |
| — | 阿拉伯语等 RTL | **明确不支持**，见 3.4 | — |

**每种语言的交付范围**：

- [ ] 游戏内全部 UI 文案
- [ ] 麻将术语表（需先建立中英对照标准词表，全语言复用）
- [ ] 新手引导与规则说明（**最难，需重写而非翻译**）
- [ ] 商店描述、关键词、截图内嵌文字
- [ ] 隐私政策与用户协议（法务文本，需专业翻译）
- [ ] 应用名与图标（评估是否需要地区化，见 3.2）
- [ ] 无需 VO ✅

## 五、商店文案本地化范围

即使 App 内只有中文，商店页面仍需按以下矩阵准备。

| 素材 | Google Play | App Store | 首发语言 |
|---|---|---|---|
| 应用名称 | 30 字符内 | 30 字符内 | 简体中文 |
| 简短描述 / 副标题 | 80 字符 | 30 字符 | 简体中文 |
| 完整描述 | 4000 字符 | 4000 字符 | 简体中文 |
| 关键词 | 无独立字段（含在描述中） | 100 字符 | 简体中文 |
| 截图内嵌文字 | 建议加中文卖点标注 | 同左 | 简体中文 |
| 隐私政策 URL | 必填 | 必填 | 简体中文 |
| 客服邮箱 | 必填 | 必填 | — |

**默认语言设置建议**：

- Google Play 默认语言设为 **简体中文（中国）**
- App Store 主要语言设为 **简体中文**
- 两个商店都**只添加中文一种语言**。不要用机翻填英文——机翻的商店描述会显著拉低转化率，也可能触发商店的低质量内容审查。

## 六、字符串冻结规则

从**提交商店前 48 小时**起进入字符串冻结期。

### 冻结期内禁止

- 修改任何玩家可见文案（UI、提示、日志、错误消息）
- 修改商店描述与截图内嵌文字
- 修改应用名称

### 冻结期内允许

- 修复 Blocker 级功能缺陷（不涉及文案）
- 修正**明确的错别字**（需发布运营负责人书面确认，且不得改变语义）

### 解冻

版本成功发布后自动解冻。

### 热修例外

热修（hotfix）可以修改文案，但必须：

1. 记录在 `补丁说明.md` 的内部变更日志中
2. 说明为何无法等到下个常规版本
3. 事后补齐字符串表同步（若 L1 已完成）

## 八、给用户的一句话总结

**首发就用中文，别折腾多语言。** 四川麻将本来就是给懂它的人玩的，翻译成英文不懂的人还是不懂。

但请务必在首发前花半天做完三件小事：**统一游戏名字**、**把 iOS 的默认语言从英文改成中文**、**写好隐私政策**。这三件不做，商店会驳回。

另外提醒一句：游戏图标上的红「發」字加上金币和排行榜，在海外商店眼里可能被当成赌博应用。首发只面向中文市场问题不大，但**分级问卷里一定要如实勾选「模拟赌博元素」**——瞒报被查出来，后果比如实申报严重得多。

好消息是：这游戏**一句配音都没有**，全是提示音效。所以以后真想做多语言，成本只有翻译文字，不用重录任何声音。晚做不吃亏。
