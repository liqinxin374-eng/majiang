## 二、关键发现（超出任务书范围，请主理人重点关注）

编制过程中发现 5 项任务书未提及、但直接影响方案可行性的事实：

### 🔴 发现 1：实际存在的是**五套**名字，不是四套

任务书列了 4 套。实扫发现**第 5 套**：

```
index.html:6        <title>科幻四川麻将「血战到底」全息控制台</title>
showroom.html:6     <title>科幻四川麻将 - 界面组件展示柜</title>
```

`<title>` 是**用户可见**的（浏览器标签页、PWA 桌面图标名、微信/QQ 分享卡片标题、搜索引擎标题）。
遗漏它会导致：改完包名和 App 名之后，玩家在浏览器里看到的仍然是「科幻四川麻将……全息控制台」。
**本方案已将其纳入改动清单（W-1）。**

### 🔴 发现 2：品牌名与现有美术主题存在**根本性冲突** — 需主理人决策

产品定名「**仙侠**麻将」，但当前项目的整体视觉与文案是**科幻 / 赛博朋克**风格：

| 证据 | 位置 |
|---|---|
| 「全息控制台」 | `index.html:6` |
| 「科幻」主题缩略图 | `theme_sci_fi_thumb.png` |
| AI 对手命名：矩阵猫 / 赛博飞鸟 / 霓虹狼 | `src/app/main.js` |
| 头像资源：`avatar_cyber_bird.png` / `avatar_matrix_cat.png` / `avatar_neon_wolf.png` | 项目根目录 |
| 霓虹青/品红配色、`holo-alert` 全息弹窗 | `style.css` / `src/app/main.js` |

**风险**：玩家在商店看到「仙侠麻将」下载后进入赛博朋克霓虹界面，预期严重错位 → 差评、退款、商店"描述与实际不符"审核风险。

**这不是命名方案能解决的问题**，需主理人在三条路里选：
- **A. 改名迁就美术**：产品名走科幻向（但用户已拍板「仙侠麻将」，需回退决策）
- **B. 改美术迁就名**：立项仙侠皮肤重做（涉及林绘澄，工作量大，影响排期）
- **C. 先上线后迭代**：本次仅统一命名，美术风格作为已知品牌债记入待办，下个版本处理

> 📌 **本方案默认按 C 编制**（只做命名收敛，不动美术）。若选 A/B 请回退本方案重编。

### 🟡 发现 3：`.git` 是**空壳目录**，git 回滚完全不可用

任务书说"项目当前无 git"——实扫结果比这更需要说明：

```
$ ls -la .git/     → 空目录（无 HEAD / objects / refs）
$ git rev-parse    → fatal: not a git repository
```

`.git` 目录**存在但为空壳**。影响：
- 确认无任何 git 回滚能力，**回滚 100% 依赖手工备份**（§5）
- 这个空壳目录可能让部分工具/IDE 误判为"已是仓库"而跳过初始化提示
- **建议（待确认）**：本次改动前先 `git init` + 首次全量提交，把改名做成一个可 `git revert` 的提交。成本约 5 分钟，收益是把 §5 的手工回滚降级为一条命令。用户此前表示暂不 init，故此处仅建议，不擅自执行。

### 🟡 发现 4：`scifi-mahjong-*` 是**玩家存档键**，改了会清空玩家数据

```
src/app/main.js:230  const GAME_SETTINGS_STORAGE_KEY  = 'scifi-mahjong-game-settings';
src/app/main.js:254  const ONLINE_PLAYER_STORAGE_KEY  = 'scifi-mahjong-online-player-id';
src/app/main.js:255  const LAST_ROOM_STORAGE_KEY      = 'scifi-mahjong-last-room';
```

这三个是 `localStorage` 的 **key 字面量**，实际用于读写玩家数据（`getItem`/`setItem`，见 234/243/262/264/1459/1919/1924 行）。

**一旦修改，所有老玩家的游戏设置、在线身份 ID、最后房间号全部丢失**（旧 key 数据变成孤儿，读不出来）。
**判定：绝对不改**，理由见 §3。

### 🟡 发现 5：Android 示例测试**已是坏的**，与本次改名无关

```
android/app/src/androidTest/.../ExampleInstrumentedTest.java:24
  assertEquals("com.getcapacitor.app", appContext.getPackageName());
```

断言的是 Capacitor 模板默认包名 `com.getcapacitor.app`，与当前实际包名 `com.zhijianmahjong.game` **本来就不一致**——这个测试现在就是失败的，是模板残留。
**判定：本次不动**，避免与改名工作混淆。但需告知严守真，别把它算成改名引入的回归。

## 三、用户可见名 vs 内部工程名 — 改 / 不改判定

**核心原则：只改玩家能看到的，内部代号一律保留。** 扩大改动面 = 无收益地放大回归风险。

### 3.1 ✅ 必须改（用户可见）

| 标识 | 可见位置 | 理由 |
|---|---|---|
| `发财麻将` | 首页大标题 H1 | 玩家进游戏第一眼 |
| `指尖麻将` | 手机桌面图标名、App 切换器 | 系统级可见 |
| `科幻四川麻将「血战到底」全息控制台` | 浏览器标签、分享卡片 | Web 端可见（发现 1） |
| `com.zhijianmahjong.game` | 商店 URL、系统设置应用列表 | **上架后永久锁定** |

### 3.2 ❌ 保留不改（内部工程名 / 代号）

| 标识 | 位置 | 保留理由 |
|---|---|---|
| `scifi-mahjong-ui` | `package.json:2` `name` | **纯内部包名**。`private: true` 不发布 npm；不出现在任何构建产物或玩家界面。改它需同步改 `package-lock.json`，可能触发依赖树重装。**零收益，有风险。** |
| `scifi-mahjong-game-settings` 等 3 个 | `src/app/main.js:230/254/255` | **玩家存档键**。改 = 清空所有老玩家数据（发现 4）。若未来确需改，必须写数据迁移脚本（读旧 key → 写新 key → 删旧 key），本次不做。 |
| `mahjong-mobile-table-size` | `src/app/main.js`（UI 缩放存档键） | 同上，存档键，且不含旧品牌词。 |
| `com.getcapacitor.myapp` | `androidTest/` `test/` | Capacitor 模板测试包，与产品包名无关（发现 5）。 |
| CSS 类名 `mahjong-table` / `mahjong-tile` 等 | `style.css` / `index.html` | 通用词 `mahjong`，非品牌标识，不含旧名。改动面巨大且零收益。 |
| 目录名 `mahjong_108_tiles_design` | 项目根 | 内部设计资产目录，不可见。 |
| 仓库 / 根目录名 `发财` | 文件系统路径 | **不改**。改根目录名会打断所有绝对路径引用、IDE 配置、本方案自身的路径。属"自找麻烦"典型。 |

> 💡 **回答任务书 §2 的核心问题**：`scifi-mahjong-ui` 确实是内部工程名（npm 包名），**保留**。
> 但要注意它与 `src/app/main.js` 里的 `scifi-mahjong-*` 存档键**是两回事**——前者无害，后者是数据键，两者都保留，但理由不同。

### 3.3 ⚙️ 生成物 — 不手改，靠重新构建覆盖

以下文件含旧标识，但都是 `npm run build` / `npx cap sync` 的**产物**。手改会在下次构建时被覆盖，且制造"改了又变回去"的错觉。

| `ios/App/App/public/**` | `cap sync` ← `dist/` |
| `android/app/build/**`（约 150+ 处命中） | Gradle 构建中间产物，可整个删除重建 |

## 六、实施顺序建议

**分 4 批执行，每批独立验证，任一批失败即就地回退，不往下走。**

```
第 0 批：备份            →  第 1 批：Capacitor 锚点
                              ↓
第 2 批：Android  ←──── 依赖 ────→  第 2' 批：iOS   （二者互不依赖，可并行）
                              ↓
                         第 3 批：Web
                              ↓
                         第 4 批：文档
```

### 第 0 批 · 备份（必做前置）
执行 §5.1。**验证**：确认 `Backup/rename-20260810/` 下 15 个文件 + 包目录齐全，逐个打开抽查非空。

### 第 1 批 · Capacitor（C-1、C-2）— **必须最先**
**为什么先做**：`capacitor.config.json` 是 `appId`/`appName` 的**单一真源**。后续 `cap sync` 会把它同步进 Android/iOS 的 assets。先改它，能让后面每次 sync 都带上正确值；顺序颠倒会反复覆盖出脏状态。
**验证**：`npx cap sync` 无报错。

### 第 2 批 · Android（A-1 ~ A-8）— **风险最高，单独一批**
**内部顺序**：A-8 目录移动 → A-7 包声明 → A-1/A-2 gradle → A-3~A-6 strings.xml
**为什么这个顺序**：先把代码结构（目录+包声明）改对，再改 gradle 让构建配置对齐；反过来会出现"gradle 指向的 namespace 无对应目录"的中间态。
**验证**：Gradle Sync 通过 → `assembleDebug` 成功 → 安装到真机 → 桌面图标显示「仙侠麻将」→ `adb shell pm list packages | grep xianxia` 命中新包名。
**注意**：安装前先卸载旧包 `com.zhijianmahjong.game`。

### 第 2' 批 · iOS（I-1 ~ I-3）— 可与第 2 批并行
**为什么可并行**：iOS 与 Android 无任何文件级交叉依赖，共同上游只有第 1 批。
**验证**：Xcode 能打开工程 → Debug **和** Release 两个 configuration 的 Bundle ID 都显示新值 → 真机跑起来图标名为「仙侠麻将」。

### 第 3 批 · Web（W-1 ~ W-3）
**为什么放这**：Web 改的是 `index.html`，而 `dist/` 会被 `cap sync` 灌进两端 assets。放在双端工程配置改完之后，最后统一 `npm run build && npx cap sync` 一次性铺平。
**验证**：`npm run build` → 浏览器标签页与首页 H1 均为新名 → `dist/index.html` 已含新名。

### 第 4 批 · 文档（D-1 ~ D-12）
**为什么最后**：文档不影响构建，且量最大。前面任一批回退了，文档就不用改，省一次返工。
**特别注意**：D-5、D-10 需人工判读，不可全局替换（理由见 §4.5）。
