## 零、先读这一节：三个可能推翻发布计划的前置问题

在准备任何素材之前，请用户先确认下面三件事。它们不是"注意事项"，是**可能直接决定能不能上架**的硬约束。

### 0.1 🔴 中国大陆安卓商店：棋牌类游戏基本拿不到版号

在中国大陆的应用商店（华为、小米、OPPO、vivo、应用宝等）上架游戏，需要：

1. **软件著作权登记**（软著，约 30～60 天）
2. **网络游戏出版物号（版号，NPPA）**

而**棋牌 / 麻将类游戏的版号已长期基本停止发放**。这意味着：

> **《发财麻将》几乎不可能通过中国大陆安卓应用商店的正规上架渠道。**

**现实可行的分发路径**：

| 路径 | 可行性 | 说明 |
|---|---|---|
| Web 网页版（自有域名） | ✅ 最可行 | 无需版号，即开即玩，回滚最快 |
| Google Play（面向海外/港澳台） | ✅ 可行 | 大陆用户无法访问，但海外华人可下载 |
| App Store 中国区 | ❌ 需版号 | 同样受限 |
| App Store 海外区 | ✅ 可行 | 需 Apple 开发者账号 |
| 直接分发 APK（官网下载） | ⚠️ 可行但受限 | 无需版号，但 Android 会警告"未知来源"，且无法自动更新 |

**建议**：**以 Web 版为首发主战场**，Google Play / App Store 面向海外市场，中国大陆走网页 + 官网 APK 下载。这个结论会显著改变后续的资源投入分配，请用户优先拍板。

### 0.2 🔴 Google Play 个人开发者账号：需要 12 人封闭测试 14 天

若使用**2023 年 11 月 13 日之后注册的个人开发者账号**，Google Play 要求在能够申请正式发布之前：

- 招募**至少 12 名测试者**
- 进行**连续 14 天**的封闭测试
- 12 名测试者必须在 14 天内持续参与（opt-in 状态不能中断）

**这意味着首发时间线至少要预留 3 周**，而不是"提交完等审核"。

**处置**：请用户尽早确认能否凑齐 12 名测试者（亲友即可，需各自 Google 账号）。若凑不齐，Google Play 路径需重新评估。若使用企业账号（Organization）则无此要求。

### 0.3 🔴 有注册功能 = 必须提供账号删除入口

项目已实现注册 / 登录（`server/accountService.js`）。据此：

- **Apple**：App Store Review Guideline 5.1.1(v) 要求，允许创建账号的 App **必须在 App 内提供删除账号的入口**（不能只提供"联系客服注销"）。**这一条是硬性拒审项。**
- **Google Play**：要求提供**应用内删除路径**与**可公开访问的网页删除请求 URL**（两者都要）。

**当前项目状态**：`accountService.js` 中有 `register` / `login` / `createGuest` / `getProfile`，**没有任何删除账号的方法**。

**处置（P0，必须在提交前完成）**：

1. 服务端增加 `deleteAccount(userId)`，级联删除 users / coin_transactions / match_players 记录（`schema.sql` 已定义 `ON DELETE CASCADE`，实现时直接受益）
2. 前端在「设置」或「个人资料」中增加删除入口，含二次确认
3. 提供网页版删除请求页面 URL

> 若最终采纳 `发布清单.md` B5 的**方案 B（首发下线账号功能，只保留游客本地模式）**，则本条自动解除。**这是选择方案 B 的一个额外好处**。

Web 是本项目**风险最低、回滚最快、无需版号**的分发渠道，建议作为首发主战场。

### 3.2 缓存策略（关键）

Vite 已为 JS/CSS 生成内容哈希文件名（如 `index-C49pLpvX.js`），据此配置：

| 资源 | Cache-Control | 理由 |
|---|---|---|
| `index.html` | `no-cache, must-revalidate` | 入口必须每次校验，否则玩家永远拿不到新版本 |
| `assets/*.js`、`assets/*.css` | `public, max-age=31536000, immutable` | 文件名带哈希，可永久缓存 |
| `mahjong-tiles/*.svg` | `public, max-age=604800` | 文件名无哈希，7 天 |
| `themes/*`、`avatar_*.png` | `public, max-age=604800` | 同上 |

> ⚠️ **这是 Web 发布最容易翻车的地方**。若 `index.html` 被 CDN 缓存，玩家会持续加载旧版本，且你在服务器上看不出任何异常。历史上项目已经踩过一次样式缓存的坑（`测试清单.md` 记录：通过改 `mobile-landscape.css` 版本号强制刷新）。请务必配置正确。

## 五、回滚与热修（Hotfix）方案

### 5.1 核心认知：移动商店没有真正的回滚

这是发布运营中最容易被误解的一点，必须先讲清楚：

| 平台 | 能否回退到旧版本 | 真实机制 |
|---|---|---|
| Web | ✅ **可以，秒级** | 切换软链指向旧目录 |
| Google Play | ❌ **不能** | `versionCode` 只能增不能减。只能"停止放量"，已安装用户不会自动降级 |
| App Store | ❌ **不能** | 只能暂停分阶段发布或下架。已安装用户不会自动降级 |

**结论：一旦移动端发出去，唯一的路是"向前修复"，不是"向后回退"。** 这就是为什么必须做 Web 先行 + 分阶段发布 + 首日只放 10%。

### 5.2 Web 回滚方案（秒级，主力手段）

**部署结构**：

```
/var/www/mahjong/
├── releases/
│   ├── v1.0.0/          ← 历史版本，至少保留 3 个
│   ├── v1.0.1/
│   └── v1.0.2/
└── current -> releases/v1.0.2   ← 软链
```

**回滚操作（约 5 秒）**：

```bash
ln -sfn /var/www/mahjong/releases/v1.0.1 /var/www/mahjong/current
nginx -s reload
```

**回滚后必做**：

1. 确认 `index.html` 的 `no-cache` 头生效，玩家刷新即可拿到旧版
2. 如有 CDN，**执行缓存刷新**（否则回滚在边缘节点不生效——这是回滚失败最常见的原因）
3. 在游戏内或站点顶部挂公告说明

**演练要求**：回滚流程必须在**正式发布前实际演练一次**。没演练过的回滚方案等于没有方案。

### 5.3 Google Play 应急流程

| 严重度 | 动作 | 时效 |
|---|---|---|
| 🔴 崩溃率 > 5% / 核心不可玩 | 1. 立即 **Halt rollout**（停止放量）<br>2. 修复后以更高 `versionCode` 重新提交<br>3. 申请加急审核 | 停止放量即时生效；新版审核数小时～数天 |
| 🟡 局部问题 | 暂停放量，保持当前百分比观察 | 即时 |
| 🟢 轻微问题 | 合入下个常规版本 | — |

> 💡 分阶段发布的价值：首日只放 10%，即使出事也只有 10% 的用户受影响，且可立即冻结在 10% 不再扩大。

### 5.4 App Store 应急流程

| 严重度 | 动作 | 时效 |
|---|---|---|
| 🔴 严重 | 1. **Pause Phased Release**<br>2. 必要时 **Remove from Sale**（阻止新下载，已安装用户不受影响）<br>3. 提交修复版并申请 **Expedited Review** | 暂停即时；加急审核通常 24～48h |
| 🟡 中等 | 暂停分阶段发布，观察 | 即时 |
| 🟢 轻微 | 合入下个版本 | — |

> ⚠️ 加急审核额度有限，滥用会被 Apple 拒绝后续申请。**只用于真正的严重故障。**

### 5.5 热修（Hotfix）流程

**触发条件（满足任一）**：

- 崩溃率 > 2%
- 核心玩法不可用（无法开局 / 无法出牌 / 无法结算）
- 规则判定错误导致玩家分数错误
- 账号或金币数据错误
- 安全漏洞

**简化流程（目标 4 小时内完成）**：

| 步骤 | 内容 | 负责 |
|---|---|---|
| 1 | 确认问题、评估影响面、决定是否热修 | 发布运营 + 用户 |
| 2 | **立即止血**：Web 回滚 / 商店停止放量 | 发布运营 |
| 3 | 最小化修复，**只改必要代码**，禁止捎带其他改动 | 程基岩 |
| 4 | **必跑**：`node --test tests/*.test.js`（108 项）+ `vite build` + `checkPerformance.js` | 严守真 |
| 5 | 定向验证问题场景 + 核心回归（开局 / 定缺 / 出牌 / 碰杠胡 / 结算） | 严守真 |
| 6 | PATCH 版本 +1（如 1.0.0 → 1.0.1），三端版本号同步 | 发布运营 |
| 7 | Web 优先上线 → 观察 30 分钟 → 再提交商店 | 发布运营 |
| 8 | 补齐补丁说明与内部变更日志 | 发布运营 |
| 9 | **48 小时内**补写事故复盘 | 全员 |

**热修红线（不可妥协）**：

- ❌ 不允许跳过自动化测试。哪怕只改一个字符——`测试清单.md` 已记录过"改样式导致定缺面板被裁剪"的先例
- ❌ 不允许在热修中夹带无关功能或重构
- ❌ 不允许无备份直接改生产服务器文件
- ✅ 允许修改文案（字符串冻结的唯一例外，见 `本地化覆盖.md` 第六章）
- ✅ 必须保留完整审计记录：谁改的、改了什么、为什么、谁验的

### 5.6 发布后监控看板

| 时间点 | 检查项 | 阈值 |
|---|---|---|
| T+30min | Web 可访问性、控制台错误、核心流程冒烟 | 0 错误 |
| T+2h | Android Vitals 崩溃率 | < 1% |
| T+2h | 服务端错误日志、WebSocket 连接成功率 | 错误 < 1% |
| T+24h | 崩溃率、ANR 率、商店评分 | 崩溃 < 1%、ANR < 0.5%、评分 > 4.0 |
| T+24h | 玩家反馈邮件与商店评论 | 人工逐条阅读 |
| T+72h | 留存、完整对局完成率 | 建立基线 |
| T+7d | 发布回顾会 | 问题归档进 `发布清单.md` |

### 5.7 危机沟通模板

**严重故障对外公告**：

```
【服务状态说明】

我们发现部分玩家在 ______ 时遇到 ______ 的问题，
影响范围：______。

我们已经在 __:__ 暂停了新版本的推送，
目前正在修复，预计 ______ 前恢复。

给大家添麻烦了，实在抱歉。
进展会在这里第一时间同步。

临时办法：______
```

**沟通原则**：

1. **快过完美** — 30 分钟内先说"我们知道了、正在处理"，比 3 小时后给一份完整报告更重要
2. **说清影响面** — 不要含糊说"部分玩家"，能说清就说清
3. **给时间点** — 给不出确切时间就给下次同步时间（"1 小时后再更新一次"）
4. **不甩锅** — 不说"第三方服务问题"，玩家只认你的产品
5. **修复后回头说一句** — 说明原因和改进措施，这是把事故转化为信任的唯一机会
